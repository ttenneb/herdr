## Why the current interface cannot certify an exhaustive report path set

The accepted managed-Pi stream can authenticate a current route, accept a canonical Pi Todo-state *claim*, require a prepared typed bound-parent report, and fsync/read back an observed-only coverage marker. It cannot attest that the Pi extension actually committed that state unless its source and loaded runtime are independently verified. More importantly, it cannot see an off-server send or identify a generic prompt as a child's report. `agent.prompt` carries only target/text, `agent.send_keys` and `pane.send_text`, `pane.send_input`, and `pane.send_keys` carry only target/input; none carries a trustworthy child route. `handoff.send` has canonical sender/recipient selectors and records a bypass only for explicitly typed `kind=report` on a verifiable current route; report-like text with a different kind or generic PTY input is not exhaustively classifiable. Offline mailbox can identify some cross-parent report heads, but a pre-ready or off-server delivery need not create a journal record. The default-off direct-transport domain and non-Herdr delivery cannot be enumerated by the mailbox journal. A child-side opt-in callback cannot close sibling CLI/PTY/off-server writers; `report_coverage` returns `coverageQualified:false` intentionally.

Blocking all inputs to a covered parent's PTY, including generic CLI, pane APIs and user input, would change unrelated beta/delegation behavior, would still not prove that external paths are closed, and has not been authorized. The alternative is a separately designed, verified and enforced exclusive sender domain starting *before* the child begins work: exact managed-Pi extension provenance, canonical fsync/readback, server-ACKed route, complete control of every permitted local and external delivery path, durable pre-ready/unknown taint or clean new delegation, restart persistence, and an authorized compatibility policy for other parent senders. Coordinate any Pi-client/API design via the TPM; do not ask the child to attest exhaustive coverage unilaterally.

1. **Owner proof by code review**, consumed by TPM: enumerate accepted bound report, generic mailbox, `handoff.send`, target-only `agent.prompt` and send-keys/pane-input APIs, direct/off-server and pre-ready paths. Confirm no trustworthy sender-origin/complete pathway ledger for target-only PTY inputs, and no qualified public wire method. Stop the qualification claim if any path remains open or unobservable.
2. **Cross-epoch bypass projection**, consumed by TPM: an old explicit generic/PTY bypass (or old uncertain attempt) followed by a new exact route's Todo `done` and even a synthetic trusted marker must remain unknown; absence of a same-epoch bypass is not proof of off-server closure. Existing current-epoch bypass, unprepared head, stale epoch and mismatched report/root tests remain conservative.
3. **Store restart/race rejection**, consumed by TPM: internal requests to append `AllPathsTrusted` must fail before fsync (even with an existing observed marker), and reopening the store must show no qualified record. The connected `report_coverage` ACK must remain observed-only; preparing/sending across a replaced route still fails; beta accepted self and generic/offline paths must not silently become covered.
4. **One source verification plus one independent failure-seeking review**. Owner runs focused projection/store and accepted-stream/socket/API tests, formatting and diff checks. TPM inspects source and hunts a counterexample; further runs need an actual failure or changed risk.
